# Route table in the profile, one home per fragment, discovery through `.well-known`

**Status**: accepted, 2026-11-21. Decided in
[What is the route table's format, and how does a host declare the bindings it provides?](https://github.com/statewalker/statewalker-root/issues/184),
on the map [statewalker-root#112](https://github.com/statewalker/statewalker-root/issues/112).

## Context

[fragment-host-and-routing](2026-11-21-fragment-host-and-routing.md) fixed the prefixes: `/fragments/{id}/` locally, and `/peers/{peerId}/fragments/{id}/` across HTTPeers. Two things stayed open:

- the table that says where each fragment is served;
- how a host states what it can run.

A Durable Object's data may be written by only one runtime at a time (cellb `docs/ownership-and-durability.md`). Each fragment already ships an OpenAPI contract generated from Zod ([fragment-manifest-and-extension-points](2026-11-18-fragment-manifest-and-extension-points.md)).

## Decision

1. **The route table** is part of the user's profile on each device: `"<fragment-id>": { "host": "local" | "peer:<peerId>" | "url:<https://…>" }`. The application supplies defaults, and unlisted fragments are at home locally. Client halves always call `/fragments/{id}/…`, and the ServiceWorker forwards per the table, so moving a fragment changes no client code.
2. **One home per fragment per user.** Its DO data lives there, and devices that share it route to it. Local instances on different devices hold separate data until profiles sync.
3. **Discovery through `.well-known`**, each with its `/peers/{peerId}/…` form:
   - `/fragments/{id}/.well-known/openapi.json`: the fragment's OpenAPI document, served from the installed archive without waking its DO;
   - `/.well-known/host.json`: generated by the runtime (runtime, version, supported bindings, limits);
   - `/fragments/.well-known/index.json`: the installed fragments, filtered to what the caller may see.

   `/peers/{self}/…` answers exactly as `/fragments/…`.
4. **Moving a fragment is an explicit Move:** check bindings, install, deactivate the old home, export and import the DO data, switch the route, activate. One home serves at a time, and the old data is kept until the user confirms deleting it. Switching the route without moving data is allowed only before the fragment has any data.
5. **Placement is local by default.** A fragment needing bindings the local host lacks goes to a capable host the user picks, or is refused.

## Considered options

- **The route table in the application, or in a shared host configuration.** Rejected: placement is the user's choice per device, and profiles are where user state lives.
- **Client halves calling their home directly.** Rejected: every move would change client code, and placement logic would spread across fragments instead of sitting in the ServiceWorker.
- **Several homes per fragment, with the data synchronised between them.** Rejected: it breaks the single-writer rule of Durable Objects.
- **Fixing addresses through configuration.** Rejected: fixed `.well-known` addresses let peers, agents and other fragments discover services without prior configuration.

## Consequences

- **CellB work,** filed in cellb.dev:
  - [#198](https://github.com/statewalker/cellb.dev/issues/198): host description;
  - [#199](https://github.com/statewalker/cellb.dev/issues/199): import with a single-writer hand-over.
- **Fixed addresses.** The `.well-known` addresses become part of the platform's public contract between peers.
- **Sync.** Sharing one fragment's data across devices without a peer or URL home waits for profile sync, which is not designed yet.
