# Handoff: vcs-store-sql cannot hold git.git (webrun-vcs#399)

Ticket: [statewalker/webrun-vcs#399](https://github.com/statewalker/webrun-vcs/issues/399),
"vcs-store-sql cannot hold git.git: commits lose mergetag/extra headers and non-UTF-8 bytes"
(`needs-triage`). Written from the record of the session "Webrun-vcs repository testing"
(ended 2026-11-25), which filed the ticket but left no handoff.

## Done

- **Census of git.git in the SQLite backend.** A script stores every commit, tree and tag one at a
  time and reads each back. Of 86,441 commits, 170,166 trees and 1,017 tags, **137 commits come
  back changed**; every tree and tag round-trips byte for byte:
  - 134 lose their `mergetag` header;
  - 2 have non-UTF-8 bytes (a Latin-1 author name) turned into U+FFFD;
  - 1 loses an unknown `change-id` header.
- **Root cause is in `vcs-core`, before SQL:** the `Commit` model has no room for extra headers
  (`commit-format.ts` skips them silently), and commits are decoded with a non-fatal
  `TextDecoder`.
- **Worse:** only pack import verifies the round trip. The single-object paths (`importObject`,
  `commits.store`) silently store a different object under a different id.
- **What works:** on a 178k-object UTF-8-only history every check against native git passes, but
  SQLite is far slower and larger than the files backend (import 150.7 s vs 2.5 s, export 123.4 s
  vs 3.3 s, 547 MB vs 33 MB on disk).

## Left

  tests on the example commits, a migration and rollback note), so it can go `ready-for-agent`.
- Pick one or both fixes from the ticket: keep each commit's and tag's original bytes next to the
  searchable columns, and/or make the model lossless (ordered extra headers, names and messages as
  bytes). Either way the single-object path must refuse what it cannot rebuild.
- The change touches a storage format: the migration and rollback note is required
  (`docs/process/prevention.md`).
